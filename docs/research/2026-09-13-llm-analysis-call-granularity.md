# 内容分析应该一次调用还是分阶段调用

> 日期：2026-09-13
>
> 问题：一条已完成补全的内容，摘要、主题分类、内容价值评分和个人相关度评分应一次生成，还是拆成多次大模型调用？
>
> 后续评分决策已将内容价值与个人相关度合并为一个“综合价值分”；本报告关于调用粒度的结论不变，原问题保留为调研背景。

## 结论

qiushui-airadar 不应照搬旧项目的多阶段模型调用，也不应把多条完整内容塞进同一个批次。推荐采用：

- 普通内容：**一条内容、一个分析任务、一次模型调用**；
- 超长内容：**确定性切分、分段提取事实、一次最终综合分析**；
- TypeScript 根据模型返回的分项分计算综合价值分和推荐级别，模型不直接决定是否进入每日流。

一次综合分析同时返回摘要、主题、综合价值各分项、理由和引用依据。各评分分项保持独立字段，既覆盖内容自身质量，也结合当前画像判断对秋水的价值。

## 类似项目怎样处理

### TrendRadar：低信息量任务适合批量

TrendRadar 的 AI 筛选只把标题、来源、兴趣和标签传给模型，并按配置的批量大小处理；当前默认可以将 200 个标题放入一次分类调用。失败批次不会记为已分析，留到后续运行重试。

- [批量编排源码](https://github.com/sansan0/TrendRadar/blob/792bcc3928b1617bba09df34989fd5675c159b86/trendradar/ai/filter_pipeline.py#L317-L367)
- [批量分类输入与调用源码](https://github.com/sansan0/TrendRadar/blob/792bcc3928b1617bba09df34989fd5675c159b86/trendradar/ai/filter.py#L310-L381)

它的深度分析是另一个调用：将数量受限的热点和 RSS 标题汇总后，一次生成多个报告板块；JSON 解析失败时再请求一次修复。

- [聚合分析源码](https://github.com/sansan0/TrendRadar/blob/792bcc3928b1617bba09df34989fd5675c159b86/trendradar/ai/analyzer.py#L151-L240)

可借鉴之处是：标题分类这种输入很短、结果很小的任务可以批量处理，明显减少固定提示词和请求次数。

不能直接照搬之处是：qiushui-airadar 要根据完整正文或字幕评价内容质量。把很多篇完整内容放在一个请求中会产生上下文竞争、单条输出遗漏，并使一次失败导致整批重试，审计也难以对应到单条内容。

### Karakeep：独立任务方便恢复，但重复输入正文

Karakeep 在爬取完成后分别入队 `tag` 和 `summarize` 两类任务；推理 Worker 再根据任务类型调用不同处理器，两个状态分别记录和重试。

- [分别入队标签与摘要任务](https://github.com/karakeep-app/karakeep/blob/5a2f009e2f6d266087f2f3f527e6e384cefd6de4/apps/workers/workers/crawlerWorker.ts#L276-L303)
- [按任务类型分派和记录状态](https://github.com/karakeep-app/karakeep/blob/5a2f009e2f6d266087f2f3f527e6e384cefd6de4/apps/workers/workers/inference/inferenceWorker.ts#L21-L123)

优点是标签失败不会抹掉摘要，功能也能独立开关。代价是同一正文会分别进入标签与摘要请求，输入 Token 重复。

Karakeep 对超过上下文的正文采用直接按 Token 截断，而不是分段汇总。

- [按上下文长度截断标签和摘要输入](https://github.com/karakeep-app/karakeep/blob/5a2f009e2f6d266087f2f3f527e6e384cefd6de4/packages/shared/prompts.server.ts#L21-L90)

这种处理简单、便宜，但可能漏掉文章或长视频后半部分的关键结论，不适合 qiushui-airadar 的“完整补全后再评价”要求。

### 旧项目：阶段太多，成本和状态复杂度偏高

旧项目先用便宜模型做预筛，再分别生成深度摘要、个人价值，另有独立评分调用；普通内容可能多次进入模型。评分 Worker 还没有真正接入日常主流水线，说明过多阶段也增加了编排和状态脱节风险。

- [旧项目当前代码调研](../../../qiushuiai-aicontnet-extract/docs/working/2026-09-13-current-code-research.md)

可保留的是每次调用可审计、总分由代码计算；不保留重复提交内容和多个相互依赖的语义阶段。

## 三种方案比较

| 方案 | Token 与速度 | 失败恢复 | 结果一致性 | 是否推荐 |
| --- | --- | --- | --- | --- |
| 摘要、分类、两个评分各调一次 | 同一正文最多重复输入四次，最慢、最贵 | 可单项重试 | 不同调用可能互相矛盾 | 否 |
| 多条完整内容批量一次分析 | 固定提示词省，但上下文很大 | 一条异常可能重试整批 | 容易漏项、串内容 | 否 |
| 单条内容一次综合分析 | 正文只输入一次，通常最快最省 | 整条重试，状态简单 | 同一上下文生成全部结果 | 是 |

假设一篇正文为 10,000 个输入 Token，四次独立调用仅重复正文就接近 40,000 Token；一次综合调用只需传一次正文，再增加少量结构化字段说明。实际节省比例取决于提示词、输出长度和模型缓存，因此系统应记录真实用量后再调整，而不是预设固定节省百分比。

## 推荐方案

### 1. 普通内容：一次综合分析

输入：

- 内容身份、形态和必要来源信息；
- 完整正文、字幕或图文识别文本；
- 当前画像版本；
- 当前分析规则版本。

模型一次返回经过 schema 校验的结果：

- 中文摘要；
- 主题标签；
- 综合价值各分项和简短理由；
- 支撑判断的内容依据；
- 不确定或材料不足标记。

TypeScript 再负责：

- 校验字段、分值范围和必填项；
- 按已确认公式计算展示总分；
- 按阈值确定核心精选、探索候选或不进入每日流；
- 保存调用、模型、Prompt/画像/schema 版本、Token、费用和错误；
- 结果不完整时按统一重试预算切换模型。

### 2. 超长内容：分段只提取事实，最后一次评分

当内容超过当前模型路线的安全输入上限时：

```text
完整内容
   -> TypeScript 按章节/时间切分
   -> 各段并行生成结构化事实笔记
   -> 汇总全部事实笔记
   -> 一次生成最终摘要、主题和两维评分
```

分段阶段不评分，避免不同片段产生互相冲突的分数。只有最终调用生成一份正式结果。

不建议像 Karakeep 一样直接截掉尾部；确需限制成本时，应让任务明确失败或等待人工处理，不能假装已经完整分析。

### 3. 一条内容一个任务，不做完整内容批处理

Worker 可以并行处理多条内容，但每次模型请求只对应一条内容。这样一条失败只重试一条，供应商切换、Token、费用和结果证据也能准确归属。

TrendRadar 的批量标题分类可以留作未来成本优化参考，但本期不增加一个可能使内容无完整评分的预筛阶段。

## 为什么最适合当前范围

1. 本期所有完成补全的内容都需要形成统一总分，不能只给“筛中的内容”完整分析。
2. 本期画像固定，画像变化后也不重算历史内容，因此没有必要为了未来单独重算相关度而重复调用正文。
3. 一次调用最省正文输入 Token，状态只需成功或失败，恢复和审计最简单。
4. 综合价值的各个分项在同一次调用中共享对正文的理解，并保持可解释的独立字段。
5. 总分与推荐级别由 TypeScript 计算，可避免不同模型自行改变业务规则。

## 最终推荐口径

将“内容分析任务”定义为：对一条已完整补全的内容，使用一个模型和一个版本化结构化契约，一次生成摘要、主题与综合价值各分项；模型只提供语义判断，TypeScript 负责校验、总分、分级、持久化和副作用。超出安全输入上限时，任务内部采用分段事实提取加最终综合分析，但对外仍是一条可重试、可审计的内容分析任务。
