# 自适应文章总结提示词研究与三方案实测

- 日期：2026-09-19
- 测试内容：IBM Technology 视频《什么是 MLflow？追踪 AI 智能体与 LLM 工作流》
- 原始输入：英文字幕 7,257 个字符、约 1,229 个英文单词
- 模型：`openai-codex/gpt-5.5`
- 调用方式：三个候选系统提示词依次调用同一项目模型接口；输入、模型、输出格式保持一致
- 数据边界：本次只做实验，没有更新内容数据库或正式提示词

## 问题

当前 v4 提示词要求“完整总结”，却没有告诉模型什么信息应当舍弃。实测产生了 1,261 个汉字的总结，与数据库旧总结的 1,277 个汉字几乎相同。问题不在于没有规定固定字数，而在于没有建立明确的**信息取舍标准和停止条件**。

## 网络研究结论

1. [Minto Pyramid Principle 官方说明](https://barbaraminto.com/)强调，把所有思想组织在一个统领观点之下，并用 SCQ 识别读者真正的问题。应用到摘要时，应先给核心结论，再保留直接支撑结论的信息。
2. [OpenAI Academy 的长文阅读建议](https://academy.openai.com/public/clubs/higher-education-05x4z/blogs/read-papers-proposals-and-reports-faster-with-chatgpt-2026-05-19/)将好摘要定义为：准确捕捉主要论点、区分核心观点与支撑细节、足够简洁以便快速浏览。
3. [OpenAI 模型写作指南](https://developers.openai.com/api/docs/guides/latest-model)建议尽早说明主旨，每段只发展一个主要观点，仅在列表或表格确实更清楚时使用它们。
4. [Chain of Density 论文](https://aclanthology.org/2023.newsum-1.7/)指出，摘要存在信息量和可读性的权衡；有效方法是从稀疏摘要开始，把遗漏的重要实体融合进去，同时避免篇幅不断增长。
5. [FactCC](https://aclanthology.org/2020.emnlp-main.750/)和 [LongDocFACTScore](https://aclanthology.org/2024.lrec-main.941/)都说明，摘要评价不能只看文字重合或长度，还要检查每项陈述是否能由原文支持，长文尤其需要逐项关注事实一致性。

因此，适合 qiushui-airadar 的自适应摘要不应采用固定字数，而应同时满足：

- 有明确的核心结论；
- 支撑信息按重要性筛选；
- 删除后不影响主线理解的信息不进入摘要；
- 篇幅随独立核心观点、必要论证链和关键限制变化；
- 每项陈述都能在原文中找到依据；
- 有清楚的停止条件，避免把原文改写成另一篇长文。

# 核心结论

传统请求级监控只能看到 HTTP 状态、错误率和响应时间，无法解释多 Agent / LLM 应用为什么给出错误答案。MLflow 通过 tracing、评估和生产化配置，为多 Agent 系统提供更细粒度的 LLM 可观测性：记录每一步输入、输出、元数据，并支持用确定性规则和 LLM Judge 评估 Agent 质量。

# 关键内容

## 1. 多 Agent 应用需要超越请求级监控

在示例的房贷咨询应用中，FastAPI 路由到多个不同角色的 Agent，包括 prospector、borrower、loan officer、underwriter 和 CEO assistant；这些 Agent 会调用数据库、LLM、MCP server 等工具。
仅看到“200 OK、耗时 2.3 秒”无法判断用户为何收到错误答案。

常见问题包括：

- **静默工具失败**：MCP 工具返回空数据，Agent 仍基于不完整信息自信回答。
- **级联延迟**：慢数据库查询拖慢 LLM 调用和最终响应，但普通监控难定位瓶颈。
- **上下文溢出**：Prompt 塞入过多内容导致调用失败，用户只看到通用超时。
- **非确定性**：同一问题多次运行产生不同结果，导致难以复现 bug，也难以建立质量基线；在贷款等受监管领域还可能带来合规问题。

## 2. MLflow 的核心可观测性能力是 Trace

MLflow 是兼容 OpenTelemetry 的平台，可捕获用户请求后每一步的输入、输出和元数据。

- **Trace**：一次请求的完整记录。
- **Span**：Trace 中的单个步骤，例如一次 LLM 调用、工具调用或数据库查询。
- Span 以父子树组织，展示：
  - 谁调用了谁
  - 输入和输出是什么
  - 每一步耗时多久
  - token 数、工具参数、prompt/completion、数据库结果等信息

Trace 还可以用用户 ID 和 session ID 标记，便于回放某个用户会话中的 Agent 决策路径。

## 3. MLflow 支持开发阶段和质量评估

在用户真正使用系统前，开发者可在 notebook 中快速调整 prompt、运行 eval，获得反馈。

评估方式包括：

- **确定性评分**：如 regex 检查、exact match、延迟阈值。
- **LLM as a judge**：用第二个模型按定义标准评估 Agent 输出，例如：
  - 工具调用是否正确
  - 调用步骤是否高效
  - 回答是否相关
  - 输出是否安全
  - 是否遵守自然语言写成的业务或合规指南
    例如房贷助手可要求“保持有帮助，但不要承诺利率，保持专业”。

MLflow 还提供 **Prompt Registry**，可将表现好的系统 prompt 进行版本管理，类似 Git。

## 4. 从 Demo 到生产部署的关键配置

作者给出四点生产化建议：

1. **使用真实数据库作为 tracking server 后端**
   默认文件后端适合本机，但不适合并发写入。应使用 Postgres 或 MySQL，并将 artifacts 放到对象存储；在 Kubernetes 或 OpenShift 上应放在认证代理之后，因为 MLflow 本身不提供认证方案。

2. **开启异步 trace logging，并在高流量下采样**
   生产环境不应让 trace 导出阻塞请求路径。系统稳定后可采样 trace，但错误请求应保留 100%。

3. **谨慎选择 judge model**
   LLM Judge 默认可能使用托管 OpenAI 模型，但企业或离线环境可能不可用，应指向自有 endpoint。每次评估都是 LLM 调用，例如 500 个样本、5 个 judge 就是 2500 次推理请求；能用 regex 等确定性评分时应优先使用。

4. **把评估放进 CI，而不只是在 notebook 中运行**
   每次 prompt 或 Agent 改动都应自动运行同样的评分，像单元测试一样作为质量门禁。Prompt Registry 和版本化 eval run 可提供审计轨迹，`mlflow.genai.evaluate()` 可接入流水线执行。

## 5. MLflow 与现有生态兼容

MLflow tracing 基于 OpenTelemetry，因此 trace 不被锁定在 MLflow 内，可同时导出到 Jaeger、Grafana Tempo 等后端。
它也集成了多种 LLM provider 和 Agent framework。对支持的框架，例如 LangChain / LangGraph，可通过类似 `mlflow.langchain.autolog` 的方式自动捕获 LLM 调用、工具调用和 Agent 决策；自定义 Python glue code 可用 `@mlflow.trace` 装饰后纳入同一 trace 树。

视频以一个房贷申请聊天应用为例：系统由 FastAPI 路由到多个不同角色的 agents，包括 prospector、borrower、loan officer、underwriter 和 CEO assistant；这些 agents 会调用数据库、LLM、MCP server 等工具。作者指出，多智能体系统常见但传统监控难以发现的问题包括：MCP 工具返回空数据但 agent 继续生成答案、数据库慢查询引发级联延迟、prompt 上下文过长导致失败、以及同一问题多次运行结果不一致的非确定性问题；在贷款这类受监管领域，非确定性还会带来质量基线和合规风险。

MLflow 的核心观测单元是 trace，即一次完整请求的记录；trace 由多个 span 组成，每个 span 可对应一次 LLM 调用、工具调用或数据库查询，并按父子树展示调用关系、输入输出、耗时、token 数、工具参数、prompt/completion 对和数据库结果。trace 还可以打上 user ID 和 session ID，便于回放某个用户会话中的 agent 决策路径。开发阶段也可以在 notebook 中调 prompt、跑 eval，在真实用户访问前获得快速反馈。

在质量评估方面，视频区分了确定性评分和 LLM-as-a-judge。确定性评分可包括正则检查、精确匹配、延迟阈值；而 LLM judge 则使用另一个模型按预设标准评估 agent 输出，例如工具选择是否正确、调用步骤是否高效、回答是否相关、是否安全，以及是否符合自然语言写成的业务或合规准则。视频举例称，房贷助手的准则可以是“保持帮助性、不要承诺利率、保持专业”。MLflow 还提供 prompt registry，可把效果好的 system prompt 做版本管理，类似 Git。

视频给出四个从 demo 走向生产部署的配置建议：

| 建议 | 要点 |
|---|---|
| 使用真实数据库作为 tracking server 后端 | 默认文件后端适合本地，不适合并发写入；应使用 Postgres 或 MySQL，并把 artifacts 放到对象存储；在 Kubernetes/OpenShift 上应放在认证代理后，因为 MLflow 本身不提供认证方案 |
| 开启异步 trace logging，并在高流量下采样 | 生产环境不应让 trace 导出阻塞请求路径；系统稳定后通常不需要 100% 采集，但错误应全部保留 |
| 谨慎选择 judge model | 默认可能使用托管 OpenAI 模型，但企业或隔离环境可能需要指向自有 endpoint；judge 调用本身也是 LLM 推理调用，例如 500 条样本、5 个 judges 会产生 2500 次推理请求，因此应控制成本，并在可用时优先用确定性评分 |
| 在 CI 中评估，而不只是在 notebook 中评估 | 每次 prompt 或 agent 改动都应自动运行同一套评分，作为类似单元测试的质量门禁；prompt registry 和版本化 eval run 提供审计轨迹，可将 `mlflow.genai.evaluate()` 接入流水线执行 |

最后，作者强调 MLflow tracing 基于 OpenTelemetry，trace 不被锁定在 MLflow 内，可双写到 Jaeger、Grafana Tempo 等后端。MLflow 还支持多种 LLM provider 和 agent framework；对受支持框架可通过 `mlflow.langchain.autolog` 自动捕获 LangChain/LangGraph 操作，包括 LLM 调用、工具调用和 agent 决策；自定义 Python glue code 可用 `@mlflow.trace` 装饰后纳入同一棵 trace 树。

## 综合分析

### 方案 A

优点是逻辑层级最明显，核心结论放在最前，关键概念、四类故障、评估方法和生产配置都有覆盖。缺点是“每个下层信息支撑上层”和“完整”仍会诱导模型保留大量细节，形成多个章节。它比现有结果短，但仍需较长时间阅读。

### 方案 B

它先在内部把内容拆成独立信息，再用“必须保留、可以删除”的标准筛选，并以“最小充分摘要”作为停止条件。实际输出仍完整保留了：传统监控的问题、trace/span 的工作方式、四类主要风险、两种评估方式、四项生产建议、OpenTelemetry 和自动追踪。它舍弃了不影响主线的五个 Agent 角色名称、notebook 开发过程和 2,500 次调用示例，正文只有 582 个汉字。

这正符合产品目的：用户需要快速判断内容讲了什么和是否值得深入阅读，而不是用摘要替代原文中的所有细节。

### 方案 C

它能系统检查遗漏，并通过融合句子提高密度。实际结果比 A 更紧凑，还保留了 judge 成本示例。缺点是 Chain of Density 天然倾向不断补充显著实体；在这条字幕上生成了较大的部署表格，信息量高，但快速吸收效率不如 B。

## 推荐方案

**推荐方案 B：最小充分摘要。**

原因：

1. 不使用固定字数，而是让摘要长度由核心观点和必要逻辑决定，适用于 2,000 字和 20,000 字的不同原文。
2. “再少就损失核心意思，再多就是次要细节”提供了明确停止条件，直接解决当前总结不断扩展的问题。
3. 实测减少 53.8% 汉字，同时保留这条视频的完整主线，压缩效果明显优于 A 和 C。
4. 它显式先去重、再分级筛选，能够避免视频字幕中的重复表达和口语铺垫进入总结。
5. 表格、列表和自然段按阅读效率选择，没有强制格式导致的额外篇幅。

建议将正式提示词的第一段“进行完整总结”改为“生成最小充分摘要”，并采用方案 B 的信息分级与停止条件。垃圾判断、关键词、`long/short` 模式及 YAML 输出协议继续沿用现有格式。

## 推荐的核心总结指令

```text
你是深度内容总结助手。你的目标不是缩写原文，而是生成“最小充分摘要”：文字再少就会损失核心意思，文字再多就只是增加次要细节。

在内部先完成两步，但不要展示过程：
1. 将原文拆成独立事实、观点、方法、因果关系、案例和限制条件，并合并重复内容。
2. 按重要性筛选：必须保留能回答“原文主要说什么、为什么成立、如何运作、有什么重要边界”的信息；只起修饰、铺垫、重复、号召互动作用的信息全部删除；案例只有在没有它就无法理解观点时才保留。

输出时先写核心结论，再按逻辑写使结论成立的最少支撑信息。篇幅随内容的信息密度和逻辑复杂度变化，不按原文字数机械分配，也不设固定字数。涉及对比、分类、列举时，选择自然段、列表或 Markdown 表格中最节省阅读时间的一种。

总结必须严格忠实于原文，不添加、不推断、不扩展原文未提及的信息。
```
